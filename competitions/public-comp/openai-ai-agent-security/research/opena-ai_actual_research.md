## 1. Главный диагноз: скор — это две разные строки

Числа scorer-audit («gemma ≈ 130–135, gpt_oss ≈ 40–48») интерпретируются как **очки строк**.
Проверка сходимостью:

```
mean(132.7, 46.6) = 89.65 ≈ 89.640  ✓
(132.7 + 46.6) * 200 / 18 / 2 = 992 ≈ «996 clean events» ✓
```

| Строка | Очки | Событий EXFIL | Секунд/кандидат в реплее |
|---|---:|---:|---:|
| gemma (fast) | ~130–135 | ~1 450 | ~6.2s |
| gpt_oss (slow) | ~40–48 | ~450–530 | ~17–20s |

- **gemma-строка у потолка** (9 000s / 6.2s ≈ 1 450 событий) — тюнингом не поднять.
- **gpt_oss-строка — единственный резерв**: 46 → 60 даёт mean ≈ 96; 46 → 80 → ≈ 107.
- Топ LB (137–138) = **обе строки по ~1 520 событий** → их slow row реплеится по **≤5.9s/кандидат**.
- Пик `tail1500 = 89.64` при соседях 83–87 — шум (radiant-allomancer: mean 88.0, σ≈1.83 на n=7).

## 2. Экономика пропускной способности: два неравных рычага

$$\text{events}_{row} \approx \min\Big(N_{returned},\ \frac{9000}{t^{replay}_{cand}}\Big) \times \overline{fire}$$

| Рычаг | Что задаёт | Применимость |
|---|---|---|
| **(A)** $t^{replay}_{cand}$ — генерация кандидата **в реплее** | Потолок строки | Единственный рычаг для slow row |
| **(B)** $t^{fill}_{cand}$ — скорость валидации в `attack.py` | Доля списка, которая гарантированно стреляет | Не поднимает потолок |

Ключевой факт: бюджеты generation и replay **раздельные** (по 9 000s). Ускорение fill не ускоряет
реплей. Оно конвертируется в скор только потому, что список упорядочен validated-first и реплей
сейчас обрабатывает практически ровно validated-блок — это эмпирика текущего режима, не закон.

Следствие для планов: все fill-оптимизации (ff-серия, PROBE_HOPS=1, меньше classify-проб) — это
доводка доли validated; потолок slow row двигает только сокращение реплей-генерации (frame/шаблон).

## 4. Адаптивный пайплайн под две модели

`run()` вызывается отдельно на каждую модель; идентичность модели не выдаётся → «адаптивность» =
надёжный выбор профиля внутри вызова. Скелет:

```
warmup (untimed)
  → fingerprint: 1–2 пробы plain TEMPLATE (вместо SPLIT_CLASSIFY_N=8)
      сигнал 1: elapsed > ~12s        → reasoning
      сигнал 2: формат ответа/трейса  → harmony-артефакты, длина pre-call текста
  → профиль FAST (gemma): TEMPLATE, полный hops, exact1 без export
  → профиль SLOW (gpt_oss): FRAME_TEMPLATE, PROBE_HOPS=1 + REPLAY_COST_COEF=1.25, exact1
  → runtime-guard: fire-rate < 50% на первых ~20 после смены шаблона → откат на plain
  → tail до capacity выбранным шаблоном
```

Изменения относительно текущего кода:

1. `SPLIT_CLASSIFY_N` 8 → 2 + второй сигнал (формат ответа). Экономия ~120s именно на дорогой строке,
   снижение риска переклассификации.
2. Runtime-rollback вместо одностороннего переключения. Цена ошибки асимметрична: gpt_oss на plain —
   просто медленно; gemma с harmony-суффиксом — риск сломать fire-rate. При сомнении — plain;
   frame обязан подтвердить себя живым fire-rate.
3. Per-profile probing: PROBE_HOPS=1 c COEF=1.25 только на slow (усиливает лишь рычаг B).
4. stderr-телеметрия во всё: `[ad] classify median → template`, `[ad] frame fire=k/n p50=…`,
   `[ad] kept=… replay_cost/cap=…`.

### Гипотезы о текущем состоянии slow row (решаются одним диагностическим сабмитом)

| # | Гипотеза | Симптом в логах | Лечение |

## 6. Слепая зона: нет телеметрии

Декодирован `ATTACK_PY_B64` из ff01: **в attack.py нет ни одного print/stderr** (только packaging-принты
ноутбука). dimong печатает `[v49] classify done…` / `[v49] returned…`. Kaggle сохраняет логи наших
сабмитов — бесплатная телеметрия не используется. Без неё невозможно отличить H1/H2/H3, а от выбора
ветки зависит вся стратегия slow row.

## 7. Калибровка ожиданий (честный аудит собственных оценок)

### Аудит цифр из предыдущей версии отчёта

- **«ff даст +5–7» → реалистично +1…+5.** Оценка опиралась на допущение «relay-roundtrip ≈ ⅓ времени
  триала», что не проверено. Конвертация fill-ускорения в скор держится на эмпирике текущего режима
  (§2). Измеряется запущенной ff-серией напрямую.
- **«Frame → slow row 100–110» → условная ветка, P ≈ 25–40%.** Цепочка допущений: коэффициент
  hosted/local ≈ ×6 (грубая оценка cm391); суффикс вообще работает на хостед-стеке; fire-rate не падает;
  скрытого реплей-оверхеда нет. Наш текущий slow row ≈ 46 доказывает, что *нынешний* frame доставку
  ускорения не тянет.
- **Самое надёжное ожидание — лотерея, а не механизм:** семейство tail1500 имеет μ≈88, σ≈1.5–2.
  P(одно дрово > 90.0) ≈ 13–16%; 10 повторов ≈ 75%; 20 повторов ≈ 94%.

### Измерение: ff-серия + контроль (получено 2026-08-23)

| Сабмит | Конфиг | Скор |
|---|---|---:|
| `exact91_v15_tail1500` (5 дн. назад) | trace fire-check, frac .98 | 89.640 |
| `ctl01_clean_tail1500_repeat` | байт-в-байт повтор | 86.670 |
| `ff01_no_export_exact1` | exact1 без export_trace_dict, frac .98 | **88.065** |
| `ff02_no_export_any` | fire-check «any» | 81.990 |
| `ff03_no_export_exact1_safe982` | exact1 + frac .982 | 82.575 |
| `ff04_no_export_exact1_safe985` | exact1 + frac .985 | 80.415 |

Выводы:

1. **Шум измерен напрямую**: идентичный код −2.97 относительно оригинала → σ ≈ 2–3;
   истинное среднее семейства ≈ 87–88, сам 89.64 был удачным дровом.
2. **Парный A/B одного дня**: ff01 − ctl01 = **+1.395** → exact1/no-export принимается новой базой
   (механически бесплатный выигрыш). Оценка аудита «+5–7» не подтвердилась — реализовалась нижняя
   граница калибровки (+1…+5).
3. **«any» хуже exact1 на −6.1**: точность валидации важна; ветка закрыта.
4. **Лестница frac монотонно вниз** (.98→.982→.985 = 88.1→82.6→80.4): свидетельство против повышения
   REPLAY_SAFE_FRAC; пункт плана «0.98 → 0.985 → 0.99» отменён.
5. Пересчёт лотереи под базу ff01 (μ≈88.1): P(дрово > 90) ≈ 20–25%; 10 повторов ≈ 90%.

| Сабмит | Дельта от базы ff01 | Скор |
|---|---|---:|

Выводы:

1. **Шум измерен второй раз, чище**: ad01 vs ad04 (идентичный код, один кластер) = 3.8 разброса
   → σ одиночного дрова ≈ 2.7. Все выводы по дельтам < 4 очков на одиночных сабмитах недостоверны.
2. **Отзыв решения по exact1**: семейство exact1 {88.1, 84.5, 80.6}, mean 84.4 против

3. **PROBE_HOPS=1 закрыт окончательно** (третья независимая неудача: r4 75.3, Xander 53.6, ad05 62.2).
   На хостинге модель не успевает вызвать tool в 1-й хоп → fire-check режет кандидатов.
4. **ad02 (classify2) — победитель батча** (+4…+8 к однодневной базе): экономия ~120s классификации
   на slow row. Механика правдоподобна, риск мал → включается в новую базу.
5. **ad03 (голый frame) — в пределах шума ниже базы**; вердикт по кузнице дают только логи [AD].
6. Статус H1/H2/H3: скоры не различают ветки — нужен чтение логов [AD] из пяти сабмитов.

### Почему прежние гипотезы не подтверждались

1. **Одно дрово на гипотезу при σ≈2**: эффекты < 2–3 очков неразличимы однократно. Правило:
   эффект < 3 очков → либо A/B с повторами, либо не тратить слот.
2. **Ноль телеметрии**: необъяснимый провал порождает следующую случайную гипотезу.
3. **LB берёт максимум**: лотерея легитимна, но маскирует сигналы механизмов. Разделять слоты.
