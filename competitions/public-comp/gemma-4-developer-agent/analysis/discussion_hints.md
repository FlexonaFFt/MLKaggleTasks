# Gemma 4: обсуждения → короткое thinking

**Вердикт: следующий тест — `thinking_1024`, единственная разница с `reduced_015` — `thinking_budget: 4096 → 1024`.** Основной подтверждённый проигрыш нашей пары — время генерации, а reproduce/fix/verify дало 7/30 против 8/30, с одной discordant task. Поэтому не добавляем процедуры, агентов, тесты или tool calls: сохраняем reasoning, но просим в четыре раза меньший бюджет на каждый запрос. Это **кандидат для проверки, не установленное улучшение**. Запасной тест — `thinking_512`; консервативный откат — уже имеющийся `thinking_2048`.

Дата исследования: **2 ноября 2026, UTC**. Прочитаны вердикты прежних [LB-проверки](leaderboard_check.md) и [исследования направлений](new_direction_research.md); их гипотезы о старом scorer, LoRA и сложных архитектурах заново не выдаются за находку.

## Что реально позволяет bundle

Проверены свежескачанные [adk_submission 0.2.13](https://www.kaggle.com/api/v1/datasets/download/metric/gemma-4-developer-agent-wheelhouse/adk_submission-0.2.13-py3-none-any.whl) и [swegemma 0.2.11](https://www.kaggle.com/api/v1/datasets/download/metric/gemma-4-developer-agent-wheelhouse/swegemma-0.2.11-py3-none-any.whl). SHA-256 соответственно `f156f0bd84580ccb9334726d114d7a5481f16d3a6e2887cc4d276ced0ef8d99d` и `9ad876581f3acde8ec3c369858f0834e2b9f41a3cffce3ca42f09cb090aea9d3`; совпадение закрытому scorer не установлено.

- `adk_submission/schema.py:155–230`: разрешены T, top_p, top_k, max_output_tokens, stop_sequences, presence/frequency_penalty, response_mime_type, seed, thinking_config (budget/include/level); неизвестные поля запрещены. `swegemma/config.py:55–65`: output1..32768, thinking0..32768, default thinking4096. Убрать поле thinking — **не** отключить его.
- `adk_submission/resolvers/generation.py:359–466`: budget>0 → `extra_body.chat_template_kwargs.enable_thinking=true` и `extra_body.thinking_token_budget=N`; explicit0 → false и убирает token budget. `include_thoughts` отдельно управляет replay. CPU self-check вызвал извлечённую официальную функцию для4096/2048/1024/512/0: mapping корректен, исходный model не мутируется. Это доказательство **формирования request**, не GPU-проверка исполнения лимита vLLM.
- Бюджет одинаков для каждого запроса данного agent, а не общий task-token budget. Разные статические значения для отдельных sub_agents возможны; произвольный per-turn scheduler/«после90с thinking0» в одном LlmAgent YAML не предусмотрен. Callback references ограничены registry, Python entrypoint вне sandbox отсутствует. Ради этого не добавляем дорогие handoffs.
- `max_output_tokens` ограничивает весь ответ, включая thinking и аргументы toolcall. Сохраняем8192: снижение до1024/2048 вместе с thinking способно обрезать сам patch/tool JSON. `max_turns=80` уже намного выше observed4–20 calls; увеличение cap не чинит длительную генерацию.
- `adk_submission/server.py` действительно содержит VllmConfig/extra_args/speculative_config, но это **параметры запуска server владельцем evaluator**, а не разрешённые поля agent schema. `max_num_seqs`, speculative decoding, prefix caching, max_num_batched_tokens, TP, dtype, context length нельзя включить произвольным ключом в нашем ZIP. Ни одного измеренного переносимого .24–.29 uplift от этих knobs не найдено.
- ADK context cache и EventsCompactionConfig задаёт evaluator. В dev сохранены official `min_tokens=2048, ttl_seconds=1800, cache_intervals=10`; compaction `15/2/14336/5`, VllmServer с `tool_call_parser=gemma4`, `reasoning_parser=gemma4`, official reasoning delimiters. Установить их иначе в dev и назвать это bundle improvement было бы несопоставимо scorer.

## Один основной вариант и два запасных

| Вариант | Отличие от reduced_015 | Зачем / статус |
|---|---|---|
| **thinking_1024 — основной** | Только `thinking_budget:1024`; 8192 output, thoughts=true, T=.2, top_p=.95, 31B, prompt/tools/eval YAML идентичны | Срезать длинный хвост rumination, оставив1024 токена рассуждения на действие. Новый, качество неизвестно |
| **thinking_512 — первый backup, включён в default dev** | Только `thinking_budget:512` | Более сильная проверка именно timeout-механизма. Может освободить больше времени под edit, но сильнее риск wrong_patch. Не считать априори лучше1024 |
| **thinking_2048 — консервативный backup** | Только `thinking_budget:2048`; уже встроенный исторический bundle сохранён | Самый осторожный quality fallback, публичный sweep50/129 vs48/129; исторический LB сам по себе его не подтверждает. Не повторяем старый submit; выбирать при регрессии1024/512 |

Прогноз: ожидаем меньше долгих turns и более ранний first edit; **не обещаем** конкретное число новых solves. Если75% общего wall — thinking и все эти токены сократятся ровно в4 раза, идеализированная доля времени составит `.25 + .75/4 = .4375` исходной, то есть экономия56.25%. Это верхний сценарий, а не оценка: короткие turns уже могут быть меньше1024; extra calls/compaction и неправильные fixes съедят выигрыш. Из8 уже решённых baseline tasks нельзя потерять качество ради одного уменьшения timeout-count.

Решение по паре: сначала request/trace smoke (включено ли thinking, не оборваны ли toolcalls), затем paired-only wins/losses, timeout с patch/без patch, first edit и total wall. Положительный net без системной регрессии quality — сигнал продолжить на свежем cohort, а не автоматически отправить на LB. Никаких новых hardcoded answers для public задач.

- [submission notebook](../submission_next_thinking_1024/gemma4_thinking_1024.ipynb), [metadata](../submission_next_thinking_1024/kernel-metadata.json). Только эти два файла в новой папке. Ротация variant order, paired CSV, smoke gate, модель, official VllmServer/reasoning parser и pinned docker image сохранены.
- Обе новые bundles отличаются ровно одним sampling значением; исторические bundles побайтно сохранены. Основной submission bundle проверен на точное равенство dev `thinking_1024`. В dev manifest записываются base/effective bundle hashes и внешний watchdog.

**Расчёт dev:** v4 mean по всем60 rows253.791с ⇒ `30×3×253.791 = 6.345ч`; округлённые250с дают6.25ч, плюс однократная installation/server startup/CSV overhead. Это conservative expected runtime при сохранении прежней средней длительности, ускорение кандидатов в план не заложено.

Раньше slot был `270 + 300 verification + 90 setup = 660с`, то есть90 slots =16.5ч. С ним гарантированно30 троек не помещаются: без startup предел21 задача (учитывая15-мин reserve), при30–60мин startup —20/19. Снижать официальный timeout проверки до60–90с ради формального fit было бы нечестным изменением grader.

Теперь **только внешний watchdog на process** — `min(формальный slot,420с)`. Основание — max359.928с во всех60 v4 rows плюс60.072с запаса; stage verification timeout300 и setup allowance90 сохранены. Для90 slots это10.5ч +15мин save reserve, остаётся75мин на startup. Admission guard останавливает допуск полной тройки, если остаток не помещается; незапущенные задачи не считаются defeat. Это эмпирическая защита, **не worst-case guarantee**: любой task со setup/grading хвостом>420с будет убит и помечен timeout; такие cases надо разобрать, затем повторить весь trio с большим slot. Одинаковое правило действует на baseline и оба кандидата.

**Hidden safety:** submission не содержит dev watchdog420 и не меняет grading. Номинальные120×4.5мин=9ч agent time,3ч остаётся под charged setup/startup/overrun; финальная patch validation исключена из официальных12ч ([overview](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview)). Staff [подтверждал примерно120 задач](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/744258#3530082) 2026-09-29; это приблизительное число, не гарантия неизменного hidden size. Генерация в полёте и setup могут увеличить wall; итоговую безопасность подтверждает полный run, не одно умножение. Поднимать task cap до8мин здесь нельзя:120×8мин=16ч.

**Имя следующего Kaggle commit после dev-решения:** `--experiment --thinking-1024 --base-reduced-015` (это только предлагаемое имя; push/submit не выполнялись). Для локального git commit имя не создавалось.
